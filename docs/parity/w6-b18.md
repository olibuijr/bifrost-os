# Parity wave 6, batch b18: DNS-SD references, security events, code requirements, Bluetooth service browser

Branch `parity/w6-b18` on top of `main` (release 0.5.36). Pure Rust, std only, no new crates, no unsafe, no hardware
access, no network service. Every model opens no socket, reads no kernel feed and talks to no daemon; the event
source, daemon and shell wiring are left to later rounds. Nothing here is built or run yet (the lead builds once).

## What was built

### 1. DNS-SD operation references (`springboard/core/src/dnssd_ref.rs`)

- Mirrors the lifecycle of a DNS-SD operation reference: a reference is opened for one operation kind, replies are
  queued with `push`, pulled one at a time with `process_result` (`Ok(None)` where the C call would block), and freed
  with `deallocate`, which drops pending replies and retires the number. A deallocated reference refuses `push` and
  `process_result` with `RefError::Deallocated`.
- `Registry::open` hands out reference numbers from 1. `Ref::number` stands in for the socket descriptor (`RefSockFD`)
  and is `None` after deallocation. It is not a file descriptor.
- Kinds: Browse, Resolve, Register, QueryRecord, GetAddrInfo, EnumerateDomains, NatPortMapping.
- Not mirrored: the shared-connection form (`DNSServiceCreateConnection`), a real socket, and dispatch-queue delivery
  (`DNSServiceSetDispatchQueue`). The reply is a generic `T`, so the daemon layer can use the existing dnssd reply types.
- Official names mirrored: DNSServiceRef, DNSServiceProcessResult, DNSServiceRefSockFD, DNSServiceRefDeallocate.
  DNSServiceCreateConnection is not modelled.

### 2. Security events (`springboard/core/src/security_event.rs`)

- Eight event kinds from the official Event Types list, grouped into four BifrOSt categories:
  - Socket: `UnixSocketBind`, `UnixSocketConnect` (both phases), `SocketSuspendResume` (suspend, resume or shut down
    another process's sockets; both phases).
  - Pseudoterminal: `PtyGrant`, `PtyClose` (notify only).
  - Clock: `SetTime` (both phases).
  - Kernel: `KextLoad` (both phases), `KextUnload` (notify only).
- Phase `Authorize` asks for a verdict before the action (`Event::needs_verdict`); `Notify` reports a change that
  already happened. `Kind::phases` lists which phases each kind has.
- `Subscription` holds the (kind, phase) pairs a client wants: `subscribe` refuses a phase the kind lacks
  (`SubscribeError::NoSuchEvent`), `subscribe_category` adds every valid pair of a category, `wants` and `unsubscribe`.
- Not mirrored: the rest of the official event list (process exec and signal, file, mount, TCC and the others), the
  client connection, message delivery, verdict handling and the entitlement. Clock and kernel coverage is partial by
  design: only the set above.
- Official names mirrored (the Event Types pages): UIPC bind and connect, process suspend and resume, pseudoterminal
  grant and close, set time, kernel extension load and unload (each in its Auth and Notify form where the page lists it).

### 3. Code requirement constraints (`springboard/core/src/codereq.rs`, extended)

- The existing requirement DSL already had `allOf`, `anyOf`, the tests and the three checks. Added:
  - `ConstraintError`, a type alias of the existing `BuildError` (the same cases: empty and duplicate arguments).
  - `Scope` (OnDisk, Process, Launch) and `Constraint { scope, requirement }`, with `Constraint::all_of`,
    `Constraint::any_of` and `satisfied_by`. `satisfied_by` dispatches to `check_on_disk`, `check_process` or
    `check_launch`, so a constraint is checked in the context it names.
- Rust has no closure-based result builder, so the operator arguments come in as a `Vec`.
- Official names mirrored: allOf(requirement:), anyOf(requirement:), ConstraintError, ProcessConstraintBuilder,
  LaunchConstraintBuilder, OnDiskConstraintBuilder (as `Constraint` with a `Scope`).

### 4. Bluetooth service browser (`springboard/core/src/bt_service_browser.rs`)

- Mirrors the state of the service browser controller: an allow list of service class UUIDs (`add_allowed_uuid`,
  `add_allowed_uuids`, `clear_allowed_uuids`; empty means every service is accepted), the title, prompt and
  description text, and the option bits.
- `visible` filters a service list the caller has already queried; `choose` picks from that filtered list and records a
  `Selection { device, service }`; `results` returns it, and `cancel` clears it.
- Not mirrored: the SDP query on the radio (no radio access here), the sheet or modal panel, and the window controller
  reference (`getRef`, `withServiceBrowserControllerRef`).
- Official names mirrored: IOBluetoothServiceBrowserController (addAllowedUUID, addAllowedUUIDArray,
  clearAllowedUUIDs, getResults, getTitle, setTitle, getPrompt, setPrompt, getDescriptionText, setDescriptionText,
  getOptions, setOptions; runModal is represented by `choose`).

### Tests

- `dnssd_ref.rs`: 6 tests (order of replies, numbering, deallocate drops and retires, refused after deallocate, double
  deallocate, numbering after a free).
- `security_event.rs`: 6 tests (categories, notify-only kinds, refused subscriptions, `wants`, category counts 6 and 2
  and 8 total, verdict and unsubscribe).
- `bt_service_browser.rs`: 5 tests (no filter, filter and order, choice indexes the filtered list, duplicates and clear,
  cancel keeps text and options).
- `codereq.rs`: 4 new tests added to the existing module tests (empty and duplicate refusal, process versus on-disk
  caller handling, launch scope, unsigned on-disk scope).

## Rows skipped (reasons)

| Framework slug | Feature | Reason |
|---|---|---|
| external-accessory | USB and serial accessories | The row's own note says this is not part of the framework (USB belongs to the AccessoryAccess row, serial is not an Apple accessory API). Live USB or serial access needs hardware, which this batch may not touch. |
| force-feedback | Hardware escape commands | Driver pass-through to a device. Needs hardware. |
| force-feedback | Cooperative level and coordinate system | The matrix note says the official API marks FFDeviceSetCooperativeLevel as unimplemented in version 1.0, so there is nothing to mirror. Not re-verified in DocC in this round. |
| force-feedback | App-facing haptic request | The SDK call is a no-op because the shell's message match has no Haptic arm. Wiring it to an actuator needs hardware and a Midget test, so it cannot be honestly closed in pure Rust here. |
| fskit | Unary file system extension (user-space module) | Needs a kernel-mounted user-space file system (FUSE), an extension host and mount permissions. No pure model would be a real counterpart. |
| gss | Memory and context (object lifetime, allocation) | Rust ownership replaces the release calls; there are no GSS objects to release, so there is nothing to build. |
